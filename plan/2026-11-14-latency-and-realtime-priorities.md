# 行情、交易與圖表延遲改善順序

日期：2026-11-14（Asia/Taipei）。本計畫整合本次畫線、下單／成交通知與執行緒盤點；先保護行情與交易的即時處理，再改善圖表互動及資料載入。

## 執行順序與備份點

1. [x] 將現有待修改項目寫成本計畫。
2. [ ] 將現有尚未推送的程式、文件、測試及本計畫提交並推送 GitHub，建立修改前的備份點。
3. [ ] 完成 P1：拆出 monitor 的通知傳送並驗證。
4. P2 以後逐項實作與驗收；本次只授權先實作 P1，不把後續計畫視為已完成。

## 不變的約定

- Windows 正式部署與 macOS 均支援；使用 conda `tss`。
- 自動進出場、固定停損停利、保本維持已驗證收定 1 分 K；不改成 tick 碰線立即下單。曲線來源週期、完整歷史幾何、缺棒與健康閘門保持一致。
- 券商 I/O 仍由 trade 單一背景執行緒依序處理；callback 只能快速接收事件，不另開 session 或平行送單。目標配置 3 / 5 不代表目前實際連線量。
- 保留持久化唯一指令 ID、結果不明不重送、成交累計去重、整戶部位核對與風控版本檢查。
- 效能改善不能補造行情、券商成交時間、委託 ID 或登出成功紀錄。
- 不藉開發測試登入券商、傳送真實通知或更改正式交易狀態；服務版本變更於正常停止／啟動時生效。

## P1：monitor 通知傳送離開行情主迴圈（本次實作）

**現況：** `monitor.send_rule()` 在主迴圈直接呼叫 `telegram_notify.send_message()`；HTTP timeout 與重試會延後行情同步、指標與健康狀態發布。trade 成交通知已背景傳送，本階段不改其流程。

**修改：**

- 每個 monitor 使用固定背景通知工作者及有界佇列，不為每則市場提醒建立一條新執行緒。
- 主迴圈仍負責原有規則、開關、冷卻與 DB 唯一 claim；只提交已持久化的提醒，網路傳送及重試移至背景。
- 背景使用自己的 DB 連線記錄結果，不跨執行緒共用 monitor 的 SQLite connection；不在 DB transaction 中等待網路。
- 明確處理佇列滿、傳送失敗、暫停及關閉，避免無界累積；維持重啟不重播歷史、暫停不補發及原有去重語意。
- 通知故障不得中斷行情。關閉不得無限等待網路；未完成不得假稱發送成功。

**驗收：** 以可阻塞的假傳送器證明通知等待時 monitor 可繼續同步／發布健康；驗證單一工作者、去重、冷卻、暫停、失敗、佇列滿、關閉與 DB 連線隔離。離線測試不產生真實通知。原生 Windows／正式網路行為另列實際驗收。

## P2：補齊端到端時間紀錄與成交回報喚醒

**現況：** order callback 只更新最後事件時間；worker 完成一輪再等 0.5 秒。既有歷史不足以拆分券商回報到達、SDK cache 更新、排隊與保存耗時。

**修改：**

- 以相同 command／order 身分串連 accepted、processing、SDK 呼叫開始／完成、callback 接收、成交保存、快照發布、瀏覽器呈現及通知開始／完成。
- 訊號另記 K 收定、fetcher 發布、monitor 採用／就緒、trade 判斷時間；全部 Asia/Taipei，間隔量測使用 monotonic。
- callback 安全入列並喚醒既有交易工作者；成交狀態與券商 I/O 保持單一擁有者，處理重複／亂序、重連世代與重啟。
- 對未終結委託設有節流的回報補查；不直接把整戶同步改成無限制高頻輪詢。

**驗收：** 模擬部分成交、重複回報、漏回報、亂序、斷線與未知委託，不重送、不多計口數、不重發通知，能指出各段耗時。

## P3：交易狀態顯示不等待圖表與曲線

**現況：** Dashboard 每 2.5 秒刷新；`refreshTrading()` 等 status／state，拿到委託後又等 `loadCurves()` 才 renderOrders；期間的刷新被 refreshing 鎖略過。

**修改：**

- 拿到已確認的交易狀態即更新委託與保護顯示，曲線清單、ATR／一般 state 獨立更新。
- 評估本機 SSE 推送已持久化的狀態，保留輪詢與事件水位補漏。
- 清楚區分指令受理、送出、券商接受、部分成交及完整成交；不以畫面樂觀更新冒充券商確認。

**驗收：** 假曲線 API／state 長時間等待時，成交與撤單結果仍即時呈現；斷線過期閘門、冪等 ID 與查詢原指令保持有效。

## P4：縮短 trade 的關鍵路徑與鎖範圍

**現況：** 同一 worker／風控鎖依序執行行情、委託／部位核對、計算、保證金、Dashboard 指令及快照。加執行緒卻共用同一大鎖無法解除阻塞。

**修改：**

- 優先處理回報、現有部位保護與必要撤單，維持同一委託與指令的順序、口數及版本一致。
- 依行情版本快取完整 ATR、曲線來源幾何，減少每次送單全歷史讀取與聚合。
- 純顯示／快照組裝讀取一致的已保存狀態，移出券商工作者的重計算；CPU 密集工作優先評估獨立程序而非只加 Python thread。
- 調整保證金等低頻查詢排程，量測阻塞 RPC；優先佇列不能中斷已在等待的券商呼叫，不保證僅排優先序即可消除延遲。
- 後續評估成交 Telegram 固定工作者／佇列，保留原有成交後保存與通知去重。

**驗收：** 慢查詢／慢計算下，回報及風控處理有可觀測的延遲上限；不增加 broker session、不平行操作券商、不繞過核對。

## P5：畫線即時呈現與投影計算快取

**現況：** 保存線條後先移除草稿，再載入全圖；後端每條線投影全部目標歷史時間戳，最後才裁切。5 秒快取僅涵蓋基礎資料。

**修改：**

- 儲存等待期間保留線條呈現，成功後銜接正式資料；失敗保留草稿，避免重複保存。
- 向量化投影，保留完整來源錨點與週期幾何，只計算圖表需要的目標範圍。
- 依商品、行情版本、線條版本、來源／顯示週期與範圍快取結果；單線修改只失效必要項目，同時 miss 合併重建。
- 新增線條只更新相關圖層，避免每次全部 candles／series setData。

**驗收：** 與既有完整計算逐值對照，包含不同週期、舊錨點、缺棒、跨休市及 broker 歷史修正；驗證亂序請求不覆寫較新畫面。畫線／拖曳不依賴 API 回應，實際速度以瀏覽器量測。

## P6：1m／5m 圖表分批載入與增量更新

**修改：**

- 初次載入約 500–1,000 根，預設仍顯示 120 根；向左接近邊界時以時間游標補前一批，瀏覽器保留已載範圍。
- 新收定 K 使用更新最後一根／追加；歷史修正、撤回與版本變更另設失效機制，不能只看最後 timestamp。
- 成交量隨 K 棒同批、同時間戳更新；保留主圖底部顯示、獨立比例尺與 hover。
- 完整 ATR、delta volume 與來源曲線幾何不能按畫面視窗截斷；交易消費統一 DB，不能改讀 acquisition DB。

**驗收：** 向左補載不跳動、不重複／漏 K，切換週期與請求取消／亂序正確；成交量、箱體與線條對齊。

## P7：預先保存衍生資料與長期驗收

- 既有 1m 與經認證的 1h 資料繼續沿用；視 P5／P6 實測，才新增 monitor 維護的 5m／15m 衍生資料與顯示指標。
- 歷史價格修正、刪除或候選撤回需使相應衍生版本失效並重建，不能使用部分歷史冒充完整結果。
- 量測穩態與收盤邊界的 CPU、記憶體、DB 鎖等待、佇列深度、通知與指令延遲，至少分離 p50／p95／最大值。
- 完成 Windows 原生／券商一致性驗收，再判定正式環境的延遲改善幅度；不預先保證毫秒級硬即時。

## 診斷基準與限制

- 2026-11-14 Windows `tss` 以現有 DB 副本測得：線條讀取約 0.006 秒，新增／提交線條（含初始化及測試清理）約 0.033 秒；1m 圖資料產生約 9.9–12.1 秒，5m 約 2.1–2.7 秒，1h 約 0.3–1.2 秒。單次量測非分位數，未含 HTTP 與瀏覽器成本。1m profiler 約 81% 累計耗時在線條逐筆投影。
- 11/13 歷史案例：12:29:00 收定後，12:29:06.2 記錄訊號判斷；12:29:07 券商成交、12:30:17 通知使用的本機狀態時間、12:30:18 通知成功紀錄。較晚一次平倉到通知約 4.4 秒。歷史不能代表目前版本每次仍慢一分鐘，sent_at 也不是手機彈出時間。
- 17:09 執行緒快照為 7 個專案 Python 程序、66 個 OS threads，含框架及套件內部執行緒；核心交易並非 11 條平行下單。數量隨 HTTP／通知／套件活動變動，不作效能指標。
